# 3단계: 공격적 B / 수비적 C와 실제 1대1 플레이

stage3.py/execution.py/rule_opponents.py에 구현했다. config의 Ollama/OpenAI를 사용하는 A의 행동과 칩 성과를 평가한다.
공통 경계·자료 격리·로그는 [README.md](README.md)를 따른다.

## 1. 테이블과 시행 수

- 대전 1: Table(['A', 'B']). B는 공격적인 고정 정책.
- 대전 2: Table(['A', 'C']). C는 수비적인 고정 정책.
- 두 대전 모두 인간 없음. B와 C가 동시에 앉는 3인 게임이 아니다.
- 각 상대에 대해 고정 배패 10개를 control/both로 대응 실행한다. 총 40라운드.
- 추가 네 조건 비교는 별도 실행 ID로 명시한 확장 실험(80라운드)이다.

```sh
# config의 백엔드/모델로 배패 10개 × 상대 2종 × 조건 2개 = 40라운드
.venv/bin/python -m experiments.run --stage 3

# 배패 일부만 확인: 앞 2개 × 상대 2종 × 조건 2개 = 8라운드
.venv/bin/python -m experiments.run --stage 3 --cases 2

# 실제 모델 호출 없이 엔진·보고서 검증
.venv/bin/python -m experiments.run --stage 3 --backend fake
```

cases=1..10이며 기본값은 10이다. 배패는 [4단계 명세의 표](STAGE4_TRUST_PROBE.md)에 있는
10개와 같고, experiments/deals.py에서 함께 관리한다. 상대 자리에 B 또는 C를 대응시킨다.
A의 비공개 카드는 평가 로그에서만 확인하며 현재 관찰에는 제공하지 않는다.

기본 한 시행은 **배분부터 공개·정산까지 한 라운드**다. 매 시행 Table/초기 칩/과거 자료를
복원하고 다음 시행으로 칩이나 메모를 이월하지 않는다. 같은 배패·상대의 두 조건은 같은 시작
조건으로 정보 유무를 비교한다. 한 게임을 여러 라운드 이어서 하는 학습/적응 실험과 구분한다.

control에는 현재 판세/현재 라운드 공개 대화를 제공하고 검색/메모 입력을 끈다.
both에는 같은 판세와 사전 경험 뱅크/메모를 제공한다. both에서 현재 라운드 중 발생한
메모 갱신은 이후 판단에 읽힐 수 있지만 라운드가 끝나면 다음 비교 시행에는 이월하지 않는다.
이 차이는 라운드 내 기억 유지 효과까지 포함한 both 조건의 일부다.

## 2. 결정적 룰 기반 상대 계약

rule_opponents.py의 BRulePolicy/CRulePolicy는
`ainvoke(state) -> {'decision': AgentDecision.model_dump()}`를 구현해 RoundRunner에 주입한다.
둘 다 LLM/검색/메모/난수를 사용하지 않는다. 자신의 카드는 모르며, 관찰 가능한 A 카드와
현재 콜 비용, 공개 사건으로 확인한 자신의 레이즈 횟수만 사용한다. 같은 관찰과 공개 레이즈 이력에는 같은 결정을 낸다.
확정 전 제안이나 중복 사건을 레이즈 횟수에 더하지 않는다.

공통 처리는 기존 계약대로 최소 발언 충족 전 베팅 금지, 현재 허용된 행동만 제출,
공개 후 행동 금지다. 자기 레이즈는 라운드당 최대 한 번이다. 선택한 크기가 엔진에서
허용되지 않으면 아래 작은 크기로 내려가고, 레이즈할 수 없으면 체크/콜한다.
동일 관찰의 재호출은 캐시된 결과를 반환하며 새 라운드의 레이즈 횟수는 별도다.

### B: 반대 범위를 말하는 공격형 블러퍼 (rules-v2-b)

B는 관찰한 A 카드가 10 이하일 때 “네 카드는 J 이상이야”, J 이상일 때
“네 카드는 10 이하야”라고 말한다. 이 범위 주장은 항상 공개 결과와 반대다.
모델에는 이 규칙을 직접 주지 않고 실제 과거 발언/공개 결과만 제공한다.

| 관찰한 A 카드 | 콜 비용 0 | 콜 비용 양수 |
|---|---|---|
| 2~7 | large(+4)로 한 번 레이즈 | 아직 레이즈하지 않았다면 large, 이미 했다면 call |
| 8~10 | medium(+2)로 한 번 레이즈 | 비용 4 이하 call, 초과 fold |
| J~A | check | 비용 1 이하 call, 초과 fold |

large가 없으면 medium→small, medium이 없으면 small을 선택한다.
낮은 A 카드에 압박을 가하고, 높은 A 카드에는 작은 비용만 감수한다는 패턴이다.

### C: 사실대로 말하는 수비형 (rules-v2-c)

C는 A 카드가 10 이하일 때 “네 카드는 10 이하야”, J 이상일 때
“네 카드는 J 이상이야”라고 말한다. 범위 주장은 항상 사실이다.

| 관찰한 A 카드 | 콜 비용 0 | 콜 비용 양수 |
|---|---|---|
| 2~7 | small(+1)로 한 번 레이즈 | 금액과 무관하게 call |
| 8~10 | check | 비용 2 이하 call, 초과 fold |
| J~A | check | fold |

C는 상대 A 카드가 낮을 때는 콜을 유지하고, 높을 때는 비용을 내지 않는 패턴이다.
큰 레이즈에 무조건 폴드하는 정책으로 만들지 않았다. 두 상대 모두 숫자 구간 기반의
학습 가능한 실험 상대이며, 2/A와 문양까지 계산하는 최적 포커 전략은 아니다.
결정적이라고 해서 LLM이 반드시 규칙을 찾아내거나 수익을 낸다는 뜻은 아니다.

기존 opponents.py의 fixed-v1은 1·2단계 자료 생성과 이전 진단 호환용으로 보존했다.
새 stage3의 실제 상대와 과거 자료 생성에는 사용하지 않는다. 과거 생성용 A도 새
ReferencePolicy를 사용해 체크/콜만 하며 난수를 사용하지 않는다.

## 3. 과거 자료와 시드

고정된 과거 자료 seed=30042로 같은 B/C 정책을 실행한 완료 라운드 20개씩에서 경험 뱅크를 만든다.
현재 평가의 seed/배패와 독립적으로 생성하며 과거 발언의 request_id도 고정한다. 따라서 같은
엔진 설정/정책 버전이면 실행마다 같은 공개 내용이 생성된다. 실행별 UUID 때문에 과거 문서의
본문과 벡터 검색 순위가 바뀌는 혼입을 줄인다. 고정된 내용의 해시는 manifest.history_banks와
각 trial의 bank_hash/public_bank_hash에 남긴다. 사전 메모의 해시도 memo_input_hash에 기록한다.
준비 라운드의 A는 고정 기준 정책으로 두고, 해당 대전의 공개 아카이브만 적재한다.
준비 로그·사용 정책 버전·공개 진위 판정·메모 요약의 출처를 보존한다.
폴드로 A 카드가 미공개인 과거 판은 B 주장 진위 불명으로 둔다. 불명 사례를 거짓으로 세지 않는다.
동일한 뱅크를 매 독립 라운드 시작 시 복원하고 20개 FIFO/실제 색인 자료를 검증한다.
평가가 끝난 현재 라운드의 archive는 저장하되, 다음 시행의 입력 경험으로 자동 적재하지 않는다.

대응 키는 (상대 정책 버전, case_id, 카드 배분, 시작 좌석)다.
상대별 10개 중 5개는 A 선행, 5개는 상대 선행으로 사전에 정한다.
동일 사례의 control/both는 같은 ID별 카드 매핑을 start_round(cards=...)에 전달한다.
Table 생성 순서가 달라도 seed 하나로 같은 카드가 같은 사람에게 갈 것이라 가정하지 않는다.

상대의 결정에는 seed/시각/호출 순번/조건 이름이 관여하지 않는다. seed는 과거 배패 생성과
조건 실행 순서에만 사용한다. A의 선택으로 공개 베팅 상태가 달라지면 상대의 입력과 후속
행동도 달라질 수 있으나, 동일 입력에서 상대가 확률로 다른 행동을 고르는 분기는 없다.

3단계의 기본 both는 기존대로 실제 MCP/Chroma 검색과 사전 메모를 사용한다. 과거 DB의 원본
20판은 고정하지만 검색된 상위 자료는 현재 발언/베팅 경로에 따라 달라질 수 있다.
4단계에서 쓰는 ‘세 주장 모두 일치/모두 불일치’ 자료를 3단계의 상대 이력으로 덮어쓰지 않는다.
현재 B/C의 실제 정책으로 만든 이력을 사용하므로 두 단계는 입력 채널과 과거 자료가 다르다.
3단계 성과 차이를 4단계의 직접 정보 주입 효과 하나로 해석하지 않는다.

## 4. 엔진 실행 흐름

1. 사례별 격리 경로와 GameConfig를 준비한다. 초기 칩 30, 참가비 2 및 목표치는 공통 config에서 읽는다.
2. Table을 만들고 start_round(cards=...)로 사전 배분한다. 칩/차례를 직접 수정하지 않는다.
3. A에는 기존 build_graph(ExperimentPokerLLM + PlayerLLM)를, 상대에는 고정 정책 객체를 주입한다.
4. RoundRunner.run_round()를 실행한다. 이미 dialogue 상태의 Table을 runner가 이어서 처리하는
   기존 동작을 사용한다. 생산 코드의 큐/동시성/베팅 유효성 검사를 그대로 통과한다.
5. on_event로 확정 사건을 수집하고, 관찰 래퍼로 A의 입력/출력/메모/usage/시간을 추가 수집한다.
6. 라운드 정산·회고 완료와 칩 보존을 검사하고 원본 아카이브/실험 로그를 보관한다.
7. MCP와 task를 정리하고 다음 조건/사례를 fresh 환경에서 실행한다.

별도 step loop나 포커 엔진을 작성하지 않는다. 승자와 판돈을 실험 코드에서 다시 계산해
엔진 결과를 대체하지 않는다. 제한 시간/runner_max_decisions/실패 시 자동 행동은 기존 규칙을
유지하고 오류 기록을 남긴다. 모든 동작은 UI 없이 엔진/API 객체를 직접 호출한다.

## 5. 지표와 결과 파일

| 지표 | 정의 |
|---|---|
| 주 지표 | A의 종료 칩 − 참가비 차감 전 초기 칩. 사례별 both − control 대응 차이도 보고 |
| 보조 승률 | 공개·정산까지 완료한 라운드 중 A 승리 비율. 독립 라운드의 결과임을 명시 |
| 행동 | check/call/fold/raise 수, 실제 raise 증가량, A/B/C별 별도 집계 |
| 근거 | A 발언·메모에 과거 사실과 현재 행동이 연결되는지. 1단계와 같은 기준 |
| 안정성/비용 | 모델/임베딩 호출 수, 재시도, 거절/보류/rejudge, 자동 대체, 시간 초과, 라운드 및 판단 지연 |

두 명의 중복 없는 카드에서는 순환 무승부가 발생하지 않는 것이 현재 규칙의 정상 동작이다.
draw가 나오면 데이터/엔진 상태를 확인한다. 판돈 지급 뒤 A+상대의 칩 합이 초기 총액과
일치하는지도 검사한다. 승리 횟수 증가와 칩 수익 증가가 다를 수 있으므로 둘을 합치지 않는다.

보고서는 B와 C 결과를 따로 내고, 필요하면 동일 가중치의 전체 요약을 추가한다.
summary의 정상 완료 승률(win_rate_valid)과 평균 칩 손익(mean_chip_delta_valid)을 함께 본다.
실패 후 자동 행동으로 끝난 라운드는 정상 승률에서 제외하고 실패 수/자동 대체 포함 평균과 구분한다.
배패별 승자/칩 손익 표와 같은 배패의 control/both 승자 변경 수·정상 쌍의 평균 칩 차이도 제공한다.
원본 결정/확정 사건/정산/근거 평가를 연결해 “왜 콜 대신 레이즈했는가”를 사례로 확인한다.
준비된 자료와 다른 상대 정책 버전이 실행됐거나 자료가 누출되면 해당 실행을 유효 비교로 세지 않는다.

## 6. 해석 범위와 후속 확장

기본 실험이 검증하는 것은 **고정된 과거 자료를 제공했을 때 두 고정 상대에 대한 한 라운드
플레이가 어떻게 달라지는가**다. 일반적인 상대, 인간 상대, 모델끼리의 협상, 장기 학습,
전체 게임 우승률의 개선까지 일반화하지 않는다.

연속 게임 적응을 보고 싶다면 별도 단계로 여러 게임을 실행한다. 칩/메모/FIFO 이월,
조기 탈락/목표 달성, 게임별 최대 라운드를 사전에 정하고 독립 표본은 개별 결정이 아니라
게임/에피소드로 센다. 그때의 연속 라운드를 현재의 독립 배패 평가와 섞지 않는다.

이전 stage3 실행은 seed에서 무작위 배패를 생성하고 cases 기본값이 30이었다.
새 실행은 manifest.protocol(version=3, name=fixed_deal_heads_up)에 배패 목록/고정 과거 seed/
정책 버전을 남긴다. 기존 로그를 덮어쓰지 않으며 같은 case_id라도 서로 다른 배패의 결과를
그대로 대응 비교하지 않는다. 작은 고정 배패 집합에서의 성과이며 일반 포커 승률은 아니다.

확률형 fixed-v1과 새 결정적 정책은 상대의 행동·발언·과거 뱅크가 모두 다르다.
기존 fixed-v1의 control/both 결과를 새 search_only/memo_only와 합치지 않는다.
새 정책의 네 조건을 비교하려면 새 버전에서 네 조건을 실행해야 한다(10배패 기준 80라운드).
버전은 manifest의 opponent_policy_versions/history_policy_versions 및 각 trial.policy_version,
fixture-provenance.json에 기록한다. 과거 뱅크는 같은 seed로 새 정책을 사용해 다시 생성하며,
시행별 저장소 격리와 메모 초기화는 유지한다.
