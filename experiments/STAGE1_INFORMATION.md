# 1단계: 투입 정보가 결정과 근거를 바꾸는가

stage1.py/execution.py/fixtures.py에 구현했다. 목적은 인과 경로의 첫 확인이며 승률 평가가 아니다.
공통 경계·로그·실패 처리는 [README.md](README.md)를 따른다.

## 1. 시행 단위와 조건

30개의 고정 판단 상황을 세 조건에서 각각 평가한다. 총 90회 그래프 평가이며
기본 평가 대상은 실제 Ollama를 사용하는 A다. 상대는 Table에 합법적인 준비 행동만 넣는다.
각 비교는 별도 Table/data_dir에서 시작하며 과거 메모 입력은 세 조건 모두 빈 상태다.

| 조건 | research에 전달할 자료 |
|---|---|
| no_information | status=skipped, matches=[] |
| relevant_history | 사전 지정한 관련 경험 청크. 기존 search_experiences와 같은 ready/matches 형태 |
| unrelated_history | 길이/개수가 비슷한 무관한 경험 청크. 동일한 ready/matches 형태 |

이 단계에서는 Chroma의 검색 능력과 분리하기 위해 research 반환값만 제어한다.
그래프 route/answer/validate/remember, PlayerLLM/Ollama, MCP 메모 파일 쓰기와 엔진 행동 접수는
실제 경로를 사용한다. 이를 실제 검색 성능 시험이라고 부르지 않는다.
조건별 청크 개수는 기존 검색 limit=3 이내로 맞추고, 사실 판단에 필요한 발언과 공개 결과를
사전에 확인해 함께 제공한다. 이 단계의 matches는 실제 사건 청크가 아니라 여러 공개 사건을
묶은 fixture_public_bundle로 명시한다. 2단계의 실제 사건 청크 검색과 구분한다.

## 2. 30개 사례 구성

각 유형에 6개씩 둔다. 카드/문양/콜 비용/허용 레이즈/앞선 대화를 다양하게 하되,
동일 case_id의 세 조건은 과거 정보 외의 상태가 같아야 한다.

| 유형/사례 ID | 현재 상황과 과거 정보 | 보고 싶은 반응 |
|---|---|---|
| S1-BLUFF-01..06 | B가 A의 카드가 낮다고 주장하며 베팅. 공개 결과로 검증된 과거의 유사 거짓 주장이 여러 개 있음 | B 주장에 대한 신뢰/콜·폴드·레이즈 선택과 그 이유가 달라지는가 |
| S1-TRUTH-01..06 | 비슷한 현재 주장. 과거 유사 주장들은 공개 결과와 대체로 일치 | 단순히 “과거가 있으면 공격”하는지, 기록 내용의 방향에 반응하는지 |
| S1-AGGRESSION-01..06 | 상대의 레이즈를 받은 상황. 과거 반복 레이즈와 이후 폴드/공개 결과가 있음 | 동일 레이즈를 해석하는 방식과 응수 규모가 달라지는가 |
| S1-CONSERVATIVE-01..06 | C가 베팅. 과거에는 체크/폴드가 많고 드물게 레이즈한 사건이 있음 | 상대별 행동 패턴을 구분하는가. C의 자기 카드를 몰랐던 기록에서 강패라고 단정하지 않는가 |
| S1-LIMITED-01..06 | 최근 상대 행동에 관한 검증 가능한 경험 한 건과, 일반화하기 어려운 소수 표본 | 한 번의 결과를 고정 성향으로 단정하는지, 과거 판단을 현재 관찰과 함께 제한적으로 사용하는지 |

TRUTH/BLUFF는 현재 자기 카드에 대한 예언의 정답을 알려 주는 시험이 아니다.
A의 현재 자기 카드는 입력에서 숨긴다. 과거 주장의 진위만 당시 실제 공개 카드로 확인한다.
unrelated_history는 다른 상대·다른 상황 자료를 쓰되 B/C를 임의로 같은 인물로 해석하게 만들지 않는다.
자료에 “이번엔 레이즈해라” 같은 행동 명령은 넣지 않는다.

## 3. 엔진 경유 절차

1. fixture가 덱/카드를 정하고 Table.start_round(cards=...)를 호출한다.
2. PlayerCommand로 최소 발언과 필요한 베팅을 준비한다. A의 차례, can_speak=true,
   required_game_utterances=0, 허용 베팅이 있는 시점을 만든다.
3. Table.observe(A)와 대응하는 실제 공개 사건을 저장하고 조건별 입력 동일성을 검사한다.
4. `build_graph(ExperimentPokerLLM(...))`에 observation/event/force_bet=true를 넘긴다.
5. 모델 원문과 검증된 decision, memory_updates 및 MCP 쓰기 직후의 실제 메모를 기록한다.
6. Table.apply_decision으로 행동을 제출하고 CommandResult/새 공개 사건/상태를 기록한다.
7. 한 판단의 평가를 종료한다. 정산이 자동 발생하더라도 이 단계에서는 칩 수익의 우열을 주장하지 않는다.

그래프의 “remember 완료”와 “행동 접수 완료”를 혼동하지 않는다. 예를 들어 메모에 레이즈
계획이 있어도 엔진이 거절했다면 행동 변화의 성공 사례로 세지 않는다.

## 4. 비교할 값

- betting_signature: bet.action + raise_size + 엔진이 적용한 실제 증가량.
- dialogue_signature: speech, wait_for_dialogue, 공개 발언 존재/내용.
- 행동 변화율: no_information 대비 관련/무관 조건의 signature 차이. 둘을 별도 보고한다.
- 크기 이름 변화와 실제 칩 증가량 변화도 구분한다. maximum과 large가 같은 +4일 수 있다.
- 근거: 공개 text와 각 메모에 README의 0/1/2 점수 및 사실성 라벨을 부여한다.
- 메모: 제안이 비었는지, 실제 교체됐는지, 빈 문자열로 기존 내용을 유지했는지 구분한다.
- 오류/재시도/엔진 거절/보류, 판단 지연과 모델 호출 수도 기록한다.

결정 범위는 30개 상황에서 선택한 행동·크기의 종류와 빈도다. 확률분포/confidence를 출력받는
계약이 없으므로 모델 내부 확률을 측정했다고 표현하지 않는다. 입력 allowed_bets/raise_options는
조건 사이에서 불변이어야 하며 관련 기록으로 법적 행동 범위가 바뀌면 fixture 오류다.

## 5. 평가 예시와 해석

좋은 근거의 예: “이전 공개 결과에서 B의 비슷한 주장이 틀렸던 사례가 있어 이번 주장도
곧이곧대로 믿지는 않는다. 콜 비용을 감안해 작은 레이즈를 고려한다.”
출력 문구를 강제하지 않는다. 실제 자료에 그런 과거가 있어야 하며, 그 사유가 현재의 콜/폴드
선택을 뒷받침해도 근거 연결로 인정한다. 무조건 레이즈하는 것이 정답은 아니다.

| 관찰 | 허용하는 해석 |
|---|---|
| 행동과 근거 모두 변화 | 해당 고정 상황에서 정보에 민감한 반응을 관찰 |
| 근거 문구만 변화 | 기록 언급은 있으나 행동 효과는 확인 못함 |
| 행동만 변화, 근거 없음 | 행동 차이는 있으나 요구한 설명/메모 연결은 미충족 |
| 무관한 자료에도 비슷하게 변화 | 관련성 활용보다 추가 컨텍스트에 대한 민감성일 가능성 |
| 변화 없음 | 적어도 이 자료·상황에서는 효과 미관찰. 입력 실패인지 모델 미활용인지 로그로 확인 |

예시의 유무로 전체를 합격/불합격 처리하지 않고 30개 전체의 건수와 반례를 제시한다.
동일 조건 반복은 선택적인 안정성 검사로 별도 표시한다. temperature=0이어도 완전한 결정성을
가정하지 않으며 반복을 독립된 30개 상황으로 세지 않는다.
